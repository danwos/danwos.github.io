## Warum quawa

<Scene monster="quawa-over-the-shoulder" alt="Das quawa-Monster schaut mit der Lupe auf einen Laptop, der von selbst Code tippt" />

Mit AI entsteht Software anders: erst das Ganze grob, dann Runde für Runde
feiner. Ein Feature, das ein Agent in einer Stunde gebaut hat, sieht fertig
aus, und die Pipeline ist grün. Ob schon jemand anderes darauf aufbauen kann,
ob die Lizenzen passen oder ob die Tests überhaupt etwas prüfen, sieht man
ihm nicht an.

Grün oder rot hilft da wenig. Am Anfang ist fast alles rot, und das ist in
Ordnung – niemand verlangt in Woche zwei eine Architekturdoku. quawa misst
deshalb immer alles, auch das, was heute noch niemand fordert, und zeigt den
Abstand zum Ziel, das du dir für jetzt gesetzt hast. Eine Lücke ist eine
Information, kein kaputter Build.

## Fünf Reifegrade

| Stufe | Zustand |
|---|---|
| 0 Vibe code | was eben da ist |
| 1 Sketched | grob da – man sieht, was es werden soll |
| 2 Shaped | die Form steht und hält |
| 3 Solid | trägt Last, bereit für echte Nutzer |
| 4 Refined | im Detail durchgearbeitet, auch an den schwierigen Stellen |
| 5 Audited | von außen bestätigt |

Die Stufen beschreiben einen Zustand, keinen Arbeitsschritt. Jede Stufe
bringt neue Messungen dazu, und sie gilt erst als erreicht, wenn alle
darunter erfüllt sind. So musst du nicht alles auf einmal machen – aber eine
Stufe richtig, bevor die nächste zählt.

## Acht Bereiche

Jeder Bereich füllt die Stufen mit eigenen Messungen:

| Bereich | Zum Beispiel |
|---|---|
| Anforderungen | Feature-Beschreibungen, Abdeckung, Traceability bis zum Test |
| Dokumentation | Doku für Nutzer und Entwickler, deckt jedes Feature ab |
| Tests | Unit, Integration und E2E, Coverage, Mutationstests |
| Code-Qualität | Formatierung, Linting, Typen, Komplexität, statische Analyse |
| Security | keine Secrets, keine bekannten Lücken, Threat Model |
| Recht | eigene Lizenz, Lizenzen der Abhängigkeiten, SBOM, Datenschutz |
| Produkt und UX | danwos-Tool-Regeln, Branding, Barrierefreiheit, Übersetzungen |
| Build und Release | baut aus dem Nichts, automatisierte, signierte Releases |

## Auf einen Blick

![Reifegrad-Ringe um das quawa-Monster, ausgedachtes Beispiel](../../../assets/blog/quality-maturity/rings-front.png)

quawa zeigt den Stand als Ringe um das Logo des Tools: ein Ring pro Stufe, ein
Tortenstück pro Bereich. Das Beispiel ist ausgedacht.

- **Der dicke Block** zeigt, was erreicht ist. Das Bild bekommt Berge und
  Täler, und du siehst sofort, wo das Tool schwach ist.
- **Darüber** zeigt jede weitere Stufe ihren eigenen Stand, von Rot bis Grün.
- **Grau** zeigt, woran schon gedacht ist: dunkel, wenn die Messung
  festgelegt ist, aber noch kein Ergebnis hat, hell gestrichelt, wenn noch
  niemand beschrieben hat, wie gemessen wird. Rot schraffiert ist eine
  Messung, die selbst kaputt ist.
- **Die Linien** zeigen, was heute gilt und wohin das Projekt am Ende will.
  Stufen dazwischen sind geplant, mit Datum oder Release.

Für Karten oder ein Badge im README gibt es schlanke Varianten: nur das
Erreichte, oder alles bis zum heutigen Ziel.

## Vergleichbar durch ein festes Modell

Was auf welcher Stufe gemessen wird, legt das danwos-Modell fest – zum
Beispiel Linting und Unit-Tests ab Stufe 2. Ein Projekt sagt nur, *woher* die
Ergebnisse kommen: welcher Testlauf, welcher Report, welches Werkzeug. Strenger
geht, eigene Messungen gehen, schwächer nicht. Wer sich daran hält, bekommt
die danwos-Farben, wer abweicht, ein normales Rot-Grün. So bedeutet „Stufe 3“
bei jedem Tool dasselbe.

Im Repository liegt dafür ein Verzeichnis `.quawa/` mit einer Datei pro
Bereich, geordnet nach Stufen. Dort steht auch, ab wann eine Stufe gilt:
„Stufe 3 ab März 2027, Stufe 4 ab Version 1.0“.

## Tests, die wirklich testen

<Scene monster="quawa-fake-checkmark" left wide alt="Das quawa-Monster schaut hinter ein grünes Häkchen-Schild und findet eine Pappfront, gestützt von einem Stock" />

Sobald Agenten auf grüne Ringe hinarbeiten, schreiben sie Tests, die nichts
prüfen, oder nehmen den kürzesten Weg zu einer grünen Pipeline:

```diff
- expect(total).toEqual(42)
+ expect(total).toBeDefined()
```

Deshalb steht das, was solche Tricks aufdeckt, fest im Modell. Mutationstests
bauen kleine Fehler in den Code ein, etwa ein `>` statt `>=`, und schauen, ob
die Tests das merken. AI-gestützte Bewertungen prüfen, ob die Doku wirklich
jedes Feature abdeckt. Beides gehört zur Stufe „Refined“ – und wird trotzdem
von Anfang an gemessen.

## Was quawa nicht macht

quawa schreibt keine Tests und ersetzt keine Werkzeuge. Linter, Testläufe,
Scanner und Lizenzprüfungen gibt es schon – quawa ruft sie auf, sammelt ihre
Ergebnisse und ordnet sie den Stufen zu. Nichts davon bricht einen Build,
solange du es nicht ausdrücklich willst.

## Stand

Das Modell ist ausgearbeitet: Stufen, Bereiche, Messungen und die Darstellung.
Als Nächstes entsteht die erste Umsetzung als Kommandozeile, die lokal läuft.
Das erste Tool, das sich daran messen lässt, ist
[deciwa](/de/tools/deciwa/), danach quawa selbst und
[monsterbrain](/de/tools/monsterbrain/). Wie das Modell entstanden ist, steht
in [Wie unreif ist deine Software?](/de/blog/quality-maturity/). quawa soll eines
Tages als Open Source erscheinen; Modell und Entscheidungen stehen schon jetzt
in den [quawa-Doku](https://quawa.danwos.dev).
