## Why quawa

With AI, software comes about differently: the whole thing roughly first,
then finer round by round. A feature an agent built in an hour looks
finished, and the pipeline is green. Whether someone else can build on it
yet, whether the licenses fit or whether the tests check anything at all –
you can't tell by looking at it.

Green or red doesn't help much there. At the start almost everything is red,
and that's fine – nobody asks for architecture docs in week two. So quawa
always measures everything, including what nobody asks for today, and shows
the distance to the target you set for now. A gap is information, not a
broken build.

## Five maturity levels

| Level | State |
|---|---|
| 0 Vibe code | whatever is there |
| 1 Sketched | roughly there – you can see what it will be |
| 2 Shaped | the form stands and holds |
| 3 Solid | carries load, ready for real users |
| 4 Refined | worked through in detail, the hard parts too |
| 5 Audited | confirmed from outside |

The levels describe a state, not a work step. Every level adds new
measures, and it only counts as reached when all levels below are met. So
you don't have to do everything at once – but a level properly before the
next one counts.

## Eight areas

Every area fills the levels with its own measures:

| Area | For example |
|---|---|
| Requirements | feature descriptions, coverage, traceability down to the test |
| Documentation | docs for users and developers, covering every feature |
| Testing | unit, integration and E2E, coverage, mutation tests |
| Code health | formatting, linting, types, complexity, static analysis |
| Security | no secrets, no known vulnerabilities, threat model |
| Legal | own license, licenses of the dependencies, SBOM, privacy |
| Product and UX | danwos tool rules, branding, accessibility, translations |
| Build and release | builds from scratch, automated, signed releases |

## At a glance

![Maturity rings around the quawa monster, invented example](../../../assets/blog/quality-maturity/rings-front.png)

quawa shows the state as rings around the tool's logo: one ring per level,
one slice per area. The example is invented.

- **The thick block** shows what is reached. The picture gets hills and
  valleys, and you see right away where the tool is weak.
- **Above it**, every further level shows its own state, from red to green.
- **Gray** shows what has already been thought of: dark when the measure is
  defined but has no result yet, light and dashed when nobody has described
  yet how to measure it. Red hatching is a measurement that is itself broken.
- **The lines** show what applies today and where the project wants to end
  up. Levels in between are planned, with a date or a release.

For cards or a badge in the README there are slim variants: only what is
reached, or everything up to today's target.

## Comparable through a fixed model

What is measured on which level is set by the danwos model – for example
linting and unit tests from level 2. A project only says *where* the results
come from: which test run, which report, which tool. Stricter is fine, own
measures are fine, weaker is not. Stick to it and you get the danwos colors;
deviate and you get a plain red–green. That way "level 3" means the same for
every tool.

The repository holds a directory `.quawa/` with one file per area, ordered
by level. It also says when a level applies: "level 3 from March 2027,
level 4 from version 1.0".

## Tests that really test

As soon as agents work towards green rings, they write tests that check
nothing, or take the shortest way to a green pipeline:

```diff
- expect(total).toEqual(42)
+ expect(total).toBeDefined()
```

That's why what uncovers such tricks is part of the model. Mutation tests
plant small bugs in the code, such as a `>` instead of `>=`, and check
whether the tests notice. AI-assisted ratings check whether the docs really
cover every feature. Both belong to the "Refined" level – and are measured
from the start anyway.

## What quawa doesn't do

quawa writes no tests and replaces no tools. Linters, test runs, scanners
and license checks already exist – quawa calls them, collects their results
and maps them to the levels. None of it breaks a build unless you explicitly
want it to.

## Status

The model is worked out: levels, areas, measures and the display. Next comes
the first implementation as a command line tool that runs locally. The first
tool to be measured with it is [deciwa](/en/tools/deciwa/), then quawa
itself and [monsterbrain](/en/tools/monsterbrain/). How the model came about
is in [How Raw Is Your Software?](/en/blog/quality-maturity/). quawa is meant
to become open source one day; the model and its decisions are already in
the [quawa docs](https://quawa.danwos.dev).
